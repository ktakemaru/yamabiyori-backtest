# ヤマビヨリ本体への推奨 (提案のみ — 本体は変更しない)

作成 2026-09-19。根拠は `docs/track-b-findings.md` (Track B, Single Runs 00Z 98 ラン × 2 モデル, 2026-06-12〜09-17) と
`docs/track-a-season-tables.txt` (Track A, Previous Runs 1 年分の地上全雲量)。**全て暖候期中心の標本**で、
RH 由来の山頂雲量については寒候期の検証が無い。各項目に「確定」か「暫定 (標本不足)」を付ける。

「確定」の基準: 主要な数字の 95%CI が判定を跨がず、かつ結論が麓実況・山頂実況の両方で同じ向きであること。

---

## R1. 山頂雲量の 2 値化閾値 50% は、診断雲量のスケールと合っていない — **確定 (暖候期)、反映済み (v1.5.0, 2026-09-19)**

- 本体は `cloudcover_at_summit` (Open-Meteo が気圧面 RH から Sundqvist で診断した雲量を山頂へ内挿) を `cloud_penalty()` にそのまま入れ、
  雲海判定等で 50% 前後の閾値を使う。
- 昼間の山頂雲量は中央値 0.5〜20%、厳密 0% が 16〜29% (麓 4 座) / 42〜49% (富士山)。50% 以下が 85〜94%。
- PSS (Peirce skill score) を最大にする閾値は **3〜16% (麓実況)、1〜9% (富士山頂実況)** で、50% での PSS は 0.02〜0.19 (ほぼ無価値)。
  PSS_max は 0.4〜0.5。(findings §4.1, §4.2, §5.2)
- **非対称性 (findings §7.4)**: P(晴れ｜0%) = 0.64〜0.86 に対し P(晴れ｜>50%) = 0.00〜0.01。曇り判定はほぼ外れず、
  晴れ判定が 14〜36% 外れる = **診断の弱点は晴れ側**。登山者に痛いのは「晴れ予報で登ったら雲中」なので、
  確率への写像はスケール合わせであると同時に安全側への補正でもある。
- **写像の効果 (findings §9, leave-one-site-out, 暖候期)**: 「雲量%をそのまま確率と読む」の Brier は 0.40〜0.47 で気候値 (0.24) より悪い。
  写像後は d1〜3 で 0.18〜0.20、PSS@0.5 = 0.4。**地点別 CDF による分位変換は生値ビンの較正と同等** (差 ±0.005) なので、
  載せるなら「生値ビン + 0% 塊の別扱い」の簡単な表で足りる。効果は d7 で消える。
  麓で学習した写像は富士山頂で d7 以降に外れる (0% 塊の晴れ率が山頂では高い) ので、**76 座への一般化は未確認**。
- **推奨**: 山頂雲量を 0〜100 の「雲量%」としてそのままスコアや閾値判定に使わない。順序 (AUC 0.75〜0.81) は有効なので、
  **「晴れる確率」に変換してから使う**。0% の塊は経験確率 1 点 (d1 で 0.64〜0.86、地点依存) として扱う (§7.4)。
  Sundqvist の係数を触る必要は現時点で無い (順序が保たれているため)。
- 状態: **確定** (暖候期・日中) — 「%のままでは使えない」「確率に写像すれば d1〜3 で効く」まで。
  写像の**係数の一般化 (76 座・寒候期) は暫定**。
- **本体への反映 (2026-09-19, v1.5.0, 案 C)**: 静的テーブル `core.CLOUD_CALIBRATION_TABLE` (麓 4 地点プール、lead 束ね、PAV、
  `backtest/cloud_calibration_table.py` → `docs/cloud-calibration-table.{json,txt}`) を毎時の山頂雲量に適用し、その後に窓平均・持続ピーク。
  実効雲量は絶対値 (案 A) ではなく **同モデル d1-2 の 0% ビンの P で正規化** (案 C):
  `実効 = 100 × (1 − P(晴れ|bin, lead) / P(晴れ|0%, d1-2, 同モデル))`。
  **理由 (代表性誤差)**: このテーブルの絶対水準は麓アメダスの日照が実況なので、「山頂は晴れ・麓に谷雲」を予報の誤りとして数えている。
  山頂実況を持つ富士山では P(晴れ|0%)=0.86 で麓 4 地点の 0.64〜0.86 より明確に高く、A は山頂を系統的に過小評価する。
  行ごと正規化 (案 B) は lead 依存 (AUC 0.80→0.61 の減衰) を消してしまうので採らない。C なら d1-2 は B と同じ (0% → 実効 0%)、
  d6-10 の 0% は 1−0.505/0.737 ≈ 31% で「遠い日ほど辛い」だけが残る。3 案の実効雲量表は `docs/cloud-calibration-table.txt` 末尾。
  適用範囲: **全山頂** (検証済みは 2899m まで)。「≤2900m 全面 + 2900〜3300m ブレンド + 3300m 以上生値」案は、探索モードで
  3000m 超だけ据え置かれて日別トップ 10 入りが 15 日間で 20→40 に倍増する順位アーティファクトを生んだため却下 (全山頂なら 20→19、
  日別 Spearman 中央値 0.962→0.980)。ブレンドのコードは `CLOUD_CALIBRATION_FULL_SUMMIT_M` / `RAW_SUMMIT_M` で残してある。
  **未解決**: 槍ヶ岳 9/5 (実況晴れの参照日, 3180m) が 84.9→66.2 (生 39.8→実効 77.7)。麓学習テーブルの山頂に対する悲観性か、
  晴れの日に 39.8% が出る予報側の問題かは山頂実況が富士山 1 点では切り分けられない → R4 の富士山晴天日待ちと同じ待ち行列。
  探索モードの目安は 80→70 点に変更 (旧 80 以上の山日の変更後中央値 78、92% が 70 以上)。
  確信度は表示のみでスコアに乗っていないので lead 依存の二重計上は無い。

## R2. lead 依存の予測子選択 — **暫定 (標本不足)**

- d1〜3: 麓実況では山頂雲量 0.80/0.79/0.77 vs 地上全雲量 0.79/0.77/0.76 で **差は有意でない** (DeLong p=0.13〜0.30, n≈3,000〜3,300)。
  富士山頂の実況では d3 で山頂雲量が有意に良い (ECMWF +0.07 p=0.02, MSM +0.09 p=0.002, n=583)、d1〜2 は +0.03〜0.05 (p=0.13〜0.36)。
- d5 以降: 麓実況では地上全雲量が有意に良い (差 −0.04〜−0.06, p<0.001) が、**麓実況は内挿に構造的に不利**
  (麓の天気を測っており、内挿が「山頂だけ曇り/晴れ」を正しく当てても誤りに数える)。富士山頂の実況では d5〜10 の差は −0.01〜−0.02 で
  検出力不足 (n=583, SE 0.025〜0.033) のため判定不能。(findings §4.5)
- **推奨 (暫定)**: d1〜3 は現行の山頂内挿を維持 (山頂実況で優位の傾向)。d5 以降は「内挿を使うべき/やめるべき」のどちらも
  現標本では言えないので、**現行を変えない**。ただし製品として d5 以降の雲量表示に確信度を付ける場合、山頂雲量 (d7 で AUC 0.61、
  富士山頂 0.56) より地上全雲量 (d7 で 0.67) の方が減衰が遅いことは両実況で一貫しているので、
  「d5 以降の参考値として地上全雲量を併記する」は低リスクの選択肢。
- 状態: **暫定**。山頂実況 (富士山 7〜8 月のみ、n≈530〜583/lead) が増えるまで確定できない。

## R3. 雲量ベースのスコアを表示する実用上限 — **暫定 (暖候期のみの標本)**

- 山頂雲量 (ECMWF) の AUC: d1 0.80 → d3 0.77 → d5 0.71 → d7 0.61 → **d10 0.55** (95%CI 下限 0.53)。
- **山頂実況 (富士山頂) では d5 0.64 → d7 0.56 (CI 下限 0.51) → d10 0.55 (CI 下限 0.50)**: 登山者が山頂で経験する精度はこちらに近い
  (麓実況の値は代表性誤差で楽観的、findings §8)。
- 地上全雲量は d10 でも 0.60 (CI 下限 0.58)。Track A (通年) の地上全雲量も d7 で 0.65〜0.67。
- **推奨 (暫定)**: 雲量に基づく「晴れる/曇る」の判定や 0〜100 スコアの表示は **7 日先までを目安**にし、8 日目以降は
  「傾向 (確信度)」に落とす。本体の 14 日表示は、雲量スコアとしては d7 以降で AUC 0.55〜0.61 = ほぼ気候値と同程度、という前提で読む。
  暫定 0.55 を実用下限とした場合、山頂実況では **7 日先で下限に着く**。
- 但し書き: 標本は 2026-06〜09 (暖候期・秋雨) の 00Z ランのみ、実況は日中の日照のみ。寒候期・夜間は未検証。lead 14 日は未取得
  (d10 で 0.55 に達しているので外挿で十分と判断)。
- 状態: **暫定**。

## R4. ECMWF 帯の RH 予報は山頂で乾き側に偏る可能性 — **暫定 (代表性差と未分離)**

- 富士山 (650hPa, 観測気圧で ln(p) 内挿) の予報 RH は観測湿度より −20〜−30 ポイント (n=153〜191/lead, 2026-09-11〜18)。
  ただし観測は 80% の正時で 100% (山頂が雲中) という特異な 8 日間で、格子平均 RH と点観測の代表性差と分離できない。
- **推奨**: 現時点では本体を変えない。Phase 2 で貯まる富士山の湿度・気圧に晴天日が入ってから再評価 (findings §5.1)。
- 状態: **暫定**。

## R6. 寒候期は未検証 — 適用範囲の但し書き

- Track A (地上全雲量, 通年) では寒候期 (2026-01-15〜02-28, 45 日, n=1,483, 麓 3 地点) の d1〜3 AUC が暖候期より 0.04〜0.06 低い
  (0.73/0.71/0.69 vs 0.77/0.76/0.75)、d5〜7 は差なし (findings §4.6)。ただし lead 方向に単調でない (d3 0.69 < d5 0.72) ので
  **「暖候期より低い傾向があるが確定していない」**。地上全雲量の減衰の形は季節で変わらない。
- **RH 由来の山頂雲量は寒候期のデータが無い** (Single Runs の ecmwf_ifs025 が 2026-04-02 開始)。冬型の下層雲・筋状雲に対する
  Sundqvist 診断の順序性 (R1 の前提) は未検証。
- **推奨**: R1〜R3 を本体に反映するなら**暖候期限定の補正**として実装し、寒候期は Phase 2 のスナップショットが 2026-27 冬を
  越えてから同じ評価 (`trackb_eval`, `tracka_eval`) を再実行して決める。
- 状態: 但し書き (確定事項ではない)。

## R7. 検証できていないこと (本体の該当機能に精度の裏付けが無い)

- **夜間の雲量** (夜明け前の雲海判定、星空): 実況が日照時間なので日中しか検証していない。ひまわり赤外での検証は Phase 4 以降。
- **稜線の風**: 稜線に風の実況が無い (富士山も 2004 年に風の観測終了)。10m 風は Phase 1 で保存済みだが、本体の稜線風とは別物。
- **標高 3000m 級の山頂雲量**: 山頂実況は富士山 (3776m) の 7〜8 月のみ。2500〜3000m 帯の山頂実況は存在しない。

## R8. 「毎時 ≥0.1mm = 降水あり」は、実況では 0.5mm 未満だった時間を 7〜8 割拾っている — 事実は**確定**、推奨閾値 (ECMWF 0.2 / MSM 0.5) は**確定 (判断)、反映済み (v1.4.0, 2026-09-19)**

根拠: `backtest/precip_threshold.py` → `docs/precip-threshold-tables.txt` (Track A Previous Runs の毎時 precipitation vs アメダス 1 時間降水量、
麓 4 地点 (白馬・野辺山・奥日光・鷲倉; 富士山は降水観測なし)、2026-01-15〜02-28 + 06-11〜09-17、**全時間帯**、n=10,565/lead)。
実況の「降水あり」= ≥0.5mm/h (アメダスの分解能。実況 0.0 には無降水と 0.5mm 未満の微量の両方が入り、区別できない)。

本体で 0.1mm/h が使われている場所は 2 つで、性質が違う:
- `WET_HOUR_MSM_PRECIP_MM = 0.1` (core.py): 決定論スコアの wet hour 判定。**MSM** の毎時値に対して → MSM はネイティブ 1h なので
  丸めの問題は無い (3h ブロック内一致率 0.04)。
- `ENSEMBLE_PRECIP_WET_THRESHOLD_MM = 0.1` (detail.py): 確信度の wet_fraction と、確信度表の precip_prob / precip_mm。**ECMWF** メンバーの
  毎時値に対して → ECMWF の毎時値は **3h 積算 ÷3 を 0.1mm 丸め** (3h ブロック内一致率 1.00, api-findings §11.2) なので、
  毎時 0.1 は 3h 積算 0.15〜0.44mm を拾う。

**確定した事実 (§P-1, P-3, P-4)**

| model | lead | 予報 ≥0.1 の時間数 / 実況 ≥0.5 の時間数 (bias) | 予報 ≥0.1 のうち実況 0.0 (FAR) | うち予報がちょうど 0.1 の割合 → その実況 0.0 率 |
|---|---|---|---|---|
| ECMWF | d1 | **3.5** | **0.76** | 27% → 0.92 |
| ECMWF | d3 | 3.6 | 0.79 | 26% → 0.89 |
| ECMWF | d7 | 4.0 | 0.84 | 28% → 0.85 |
| MSM | d1 | **2.6** | **0.72** | 20% → 0.85 |
| MSM | d2 | 2.5 | 0.75 | 23% → 0.84 |

- 0.1mm/h で「降水あり」とした時間は、実況で測れる降水 (≥0.5mm) があった時間の **2.6〜4.0 倍**ある。
  実況を T±1h に広げても FAR は 0.59〜0.75 (§P-7) で、タイミング誤差では説明しきれない。
- **丸め問題のない MSM 側でも 72〜75% が実況 0.0** (ECMWF 76〜84%)。つまりこれは ÷3 丸めに起因する不具合ではなく、
  **0.1mm/h という閾値そのものが低すぎる**という指摘。÷3 丸めは ECMWF 側でそれをさらに 0.1 に張り付かせているだけ。
- 予報値は 0.1 に張り付いている: 予報 ≥0.1 の時間の 25〜30% (ECMWF) / 20〜23% (MSM) がちょうど 0.1 で、その 85〜92% は実況 0.0。
  0.2 でも 83〜89% が実況 0.0。**予報 0.1〜0.4mm/h の帯 (ECMWF で予報降水時間の 6 割) はほぼ「実況では測れない」帯**。
  実況 0.0 率が 5 割を切るのは予報 ≥1.0mm/h から (ECMWF d1 0.55、≥2.0 で 0.33)。
- 3h ブロック (ECMWF のネイティブ) で比べても同じ: 3h 積算 ≥0.3mm (= 毎時 0.1) で bias 2.2、FAR 0.64 (§P-6)。
- **本体のスコアへの影響**: wet hour は重み 1.0 でスコアの 50% を占める (`precip_penalty`) ので、この帯の時間は
  「霧雨かもしれない時間」が「雨の時間」と同じ重さで効いている。

**閾値候補 (§P-4, P-6; 暫定)**

| 候補 | ECMWF d1: bias / POD / FAR / PSS | MSM d1: bias / POD / FAR / PSS | 意味 |
|---|---|---|---|
| 0.1 (現行) | 3.5 / 0.84 / 0.76 / 0.48 | 2.6 / 0.72 / 0.72 / **0.47** | 過剰予報。MSM では PSS 最大 (見逃し最少) |
| **0.2** | 2.6 / 0.77 / 0.70 / **0.52** | 2.1 / 0.65 / 0.69 / 0.45 | ECMWF で PSS 最大。ちょうど 0.1 の時間 (92% 実況 0.0) だけ落とす。3h 積算 ≥0.6mm 相当 |
| 0.5 | 1.4 / 0.60 / 0.59 / 0.48 | 1.5 / 0.54 / 0.63 / 0.41 | 「アメダスで測れる降水」に揃える。予報降水時間が 4〜6 割減る |
| 0.7〜1.0 | 1.1〜0.8 / 0.51〜0.42 / 0.52〜0.45 / 0.44〜0.37 | 1.2〜1.0 / 0.49〜0.42 / 0.61〜0.58 / 0.38〜0.34 | bias ≈ 1 だが見逃し 5〜6 割 |

- **推奨**:
  1. **ECMWF メンバーの閾値 (`ENSEMBLE_PRECIP_WET_THRESHOLD_MM`) は 0.1 → 0.2mm/h** (= 3h 積算 0.6mm)。丸め境界 (ちょうど 0.1) の
     時間は 9 割が実況 0.0 で、落としても PSS は上がる (0.48 → 0.52, d1〜2)。確信度の precip_prob 表示も過大が減る。
  2. **MSM の閾値 (`WET_HOUR_MSM_PRECIP_MM`) は 0.1 → 0.5mm/h**。PSS 最良は 0.1 (0.47) だが、それを採らない理由:
     - この製品で空振りと見逃しは対称ではない。bias 2.6 = 実際の 2.6 倍の時間を「雨」と言う、はユーザー体験として
       「雨予報だが降っていない」が常態化する (wet hour はスコアの 50% を占める)。
     - 実況分解能が 0.5mm である以上、予報 0.1〜0.4 の帯は現データで判定不能。判定できない帯を判定に使い続ける根拠がない。
     - PSS は空振りと見逃しを対称に扱う指標なので、ここでの選択基準に適さない。
     0.5 では bias 1.5 / FAR 0.63 / POD 0.54 (MSM d1)。参照事例の唐松岳 9/6 は MSM の mm が 0.0 で moisture rule が拾った事例なので、
     この変更で参照事例は変わらない。本体に入れる前に `scratch_validate_refs.py` の参照日を再計算すること。
- 但し書き:
  - **寒候期のデータは 45 日のみ** (2026-01-15〜02-28)。残りは 6〜9 月。
  - **冬季はアメダスの雨量計が雪を取りこぼす** (転倒ます型は降雪時に過少・遅延) ため、寒候期の「実況 0.0」率は**過大評価の可能性**がある
    = 寒候期分の FAR は上限値として読む。暖候期だけでも bias と FAR の向きは変わらない (§P-2 の地点別は 6〜9 月が主)。
  - 実況は麓アメダス (点) で、予報は 5km / 25km 格子の値。稜線の降水は測っていない。
- 状態: 事実 (bias 2.6〜4.0、FAR 0.72〜0.84、0.1 張り付き、MSM でも同じ) は **確定** (通年 5 か月、n=10,565/lead、全時間帯)。
  推奨閾値 (ECMWF 0.2 / MSM 0.5) は **確定 (判断)** — コスト非対称と実況分解能を理由にした判断で、追加データで変わるものではない。
  夜間を含む全時間帯の評価なので、R1〜R3 と違い日中限定ではない。

## R9. 確信度スコアのスケーラビリティ制約 — 制約は**確定**、対策は方向のみ (実装判断は本体側)

- Open-Meteo 無料枠は member 列を変数として数える (api-findings §11.5, サーバ実装と 429 で確認)。本体の確信度リクエストは
  1 座あたり 3 変数 × 51 列 × 14 日 = **15.3 call**。探索モードで 76 座に広げると **1,163 call/回**。
- 日次上限 10,000 に対して **1 日 8 回が限界** (8 回で 9,300)。分当たり 600 も 1 回の探索の途中で超える (40 座で 612)。
  制限は IP ごとなので、**プラグイン利用者が同じ IP (社内 NAT など) から使うと利用者数分だけ早く詰まる**。スコアの精度より先にここが詰まる。
- 検討の方向 (記録のみ。実装判断は本体側で、利用者数が見えてから):
  1. **2 段構え**: 探索は決定論 (Forecast API, 1 座 1〜3 call) だけで一次スクリーニングし、候補を N 座に絞ってから確信度を計算する。
     N=10 なら 153 call/回 で 60 回/日。
  2. **山域単位の代表点にグリッドを丸める**: ECMWF ENS は 0.25° 格子なので、同じセルに入る山は 1 リクエストで済む
     (例: 唐松岳と白馬岳は同じセル)。**76 座 → 36 セル** (本体 MOUNTAINS を 0.25° に丸めて数えた) で 1,163 → 551 call/回、18 回/日。地点はメンバー列と掛け算なので効く。
  3. 確信度の変数を 3 → 2 (cloud + precip) にすれば 1 座 10.2 call (温度スプレッドの寄与は R7 と同じ未検証項目)。
- 状態: 制約 (15.3 call/座、8 回/日) は **確定**。対策は暫定。

## R11. 本体は R1 表を学習範囲の外 (夜間・暖候期外) にも当て、lead の数え方も学習と違う — 事実は**確定**、影響の大きさ (スコア差) は**未計算** (2026-09-23 記録、本体は変更しない)

- **(a) 夜間・暖候期外への適用**: `calibrated_summit_cloud_series()` は系列の全時刻に同じ表を当てる (時刻・月を見る処理が無い。
  バナーにも "night hours get the same table", "WARM-SEASON SAMPLE ONLY" とある)。一方、表の学習範囲は
  **JST 07〜17 時に終わる 1 時間** (`trackb_eval.DAY_HOURS_JST`) と **valid_time が 6〜9 月** (標本 2026-06-12〜09-18。学習コードに季節の絞り込みは無く、標本期間で決まっている)。

  - **2026-10-01 以降は全時刻が学習範囲外** (寒候期表は README 待ち項目 #2 = 2027-03 待ち)。
- **(b) lead の数え方の不一致**: 学習は `lead_day = (valid_time − 00Z ラン初期時刻) の時間 // 24 + 1`。本体の `lead_day_for()` は
  「取得日 (系列の先頭日, JST) を 1 とする暦日差」で、どのランの値かは見ていない (Forecast API のレスポンスは複数ランの継ぎ足しでラン情報も無い, api-findings §10.1)。
  `python -m backtest.r11_lead_mismatch` → [r11-lead-mismatch.txt](r11-lead-mismatch.txt) で、学習に使った (ラン, valid_time) の組に
  「本体がそのランを取得日 today に使った」と仮定して本体が引く行を数えた (時刻の算術のみ):
  - 日中 (学習範囲の時刻) で **引く lead 群が学習と違う割合**: ecmwf_ifs025 は 0〜24.4%、jma_msm は 0〜50.0% (ラン時刻 00/06/12/18Z × 取得日 当日/翌日 の 8 通り)。
    例: 00Z ランを翌日に取得すると ecmwf 17.8% / msm 27.3%、12Z ランを当日 (JST 21 時以降) に取得すると ecmwf 21.8% / msm 33.3%。
    lead_day 自体がずれる割合は最大 100% (18Z ラン × 翌日など) だが、群の境界 (ecmwf d2/d3, d5/d6、msm d2/d3) をまたぐときだけ行が変わる。
  - 参考: ecmwf の公開遅れを全ランで 7.73h (00Z の実測 1 件) と仮定し、取得時刻が一様・継ぎ足しを無視すると、日中の行違いは **約 2.9%**。
    jma_msm は 3h ごとのランでホライズンが 39h/78h と交互のため、この重み付けは未計算。
  - どの組み合わせが実際に起きているかは、取得時刻と Open-Meteo の継ぎ足し方に依存し **未確認**。
- **(c) 影響の大きさ (2026-09-23 追記、[r11-lead-mismatch.txt](r11-lead-mismatch.txt) 「影響の大きさ」)**: 行が違う時間では値は**ほぼ同じではない**。
  日中の実効雲量の差は平均 |Δ| ecmwf 15.5 / msm 9.3 ポイント (最大 26.1 / 18.6)、P(晴れ) で平均 0.11 / 0.07。向きは取得日でおおむね逆になる (当日取得は辛め = 実効雲量が平均 +3〜+6、翌日取得は甘めか ±0 = −5〜+0.1)。
  山日単位のスコア (雲量項 100·(1−c/100)^0.25 の差 = 実際のスコア差の上限) では、行が違う時間を含む山日は仮定別に 0〜25%、その山日の平均 |Δ| 0.7〜6.3 点、
  5 点以上ずれるのはその山日の 4〜50%。ecmwf の公開遅れ仮定 (7.73h) で平均すると、全山日の平均 |Δ| ≈ 0.21 点、3 点以上 ≈ 2.7%、5 点以上 ≈ 1.6%、
  符号付き平均 ≈ +0.03 点 (系統的な偏りはほぼ無い)。極端な例: ecmwf d1-2 行の (70,100] ビンは P=0 → 実効 100% なので、行が d3-5 → d1-2 に変わると
  終日曇りの山日で雲量項が 56 → 0 になる (18Z × 翌日取得の最大 55.4 点)。
- **推奨 (実装は本体側の判断)**:
  1. lead をラン初期時刻からの経過時間で数える。Open-Meteo のメタデータ API (`/data/<model>/static/meta.json` の

     mos モジュールは lead を経過時間で受け取る (`mos.calibrate(..., lead_hours=...)`)。
  2. 夜間・暖候期外の扱いを決める: mos の `on_mismatch` で「使う (`allow`、v1.5.0 と同じ)」か「補正しない (`passthrough`)」を
     呼び出し箇所に明示し、`in_scope=False` の時間には表示で「未検証の補正」と注記する。10 月以降は全時刻が該当するので、次に本体を触るときに先に決める。
- 状態: 事実は**確定**。スコアへの影響は (c) のとおり雲量項の範囲で**計算済み** (視程・降水を含む実スコアでの再計算は未実施、差はこの上限以下)。
  取得時刻の仮定に依存する点は残る。
- 冬の暫定検証 (2026-09-23、短いリード・d1-2 行のみ): 冬でも R1 が生値より有意に悪い結果は無いが、日中 09〜15 時では上積みがほぼ消える → [r1-winter-provisional.md](r1-winter-provisional.md)。

## R12. R1 の MSM 行は 900/800hPa 無しの山頂雲量で学習され、本体は 900/800hPa ありで計算している — 事実は**確定**、影響は山頂雲量・ビン・実効雲量まで**計算済み** (2026-09-23 記録、本体は変更しない)
